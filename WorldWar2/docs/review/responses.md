# Responses to review findings

Each finding that comes back from an outside review is recorded here with the decision and the reason, using the format in [findings_template.md](findings_template.md), "For us: how a finding is handled". Findings are checked against the data and the documents first (and against the sources where a finding is about a source); a finding is accepted, accepted in part, declined, deferred, marked known or answered with a request for information, and the reason is written down. Ids look like `R1-F-001` (review number, then the reviewer's own id). Accepted changes are cited by finding id in `docs/changelog.md` and in the commit message.

### R1-F-004 (claim key, claims, severity 3): `(unit_id, date, event_type)` is not a natural key; make it a duplicate warning
- **Status:** PROPOSED: deferred (keep the error for now; revisit at stated triggers), plus a documentation clarification accepted. Pending the owner's decision.
- **Checked:** `schema/claims.schema.json` (`primaryKey` is `claim_id`; `uniqueTogether` with a note); `CONTRIBUTING.md` "Claim identity"; `docs/methodology.md` "One row, one action"; the data: 566 distinct keys, 0 violations, 0 rows in `data/claim_key_exceptions.csv`, 7 unit-and-date pairs that share a day but differ in event type.
- **Decision and reason:** a balanced view. (1) **`claim_id` is already the only identity**; the key is an additional uniqueness rule that catches a duplicated row (for example the same claim entered twice by two batches). `CONTRIBUTING.md` headed it "Claim identity", which invites the reviewer's reading, so the heading should say "Duplicate guard" and state that `claim_id` is the identity. (2) The reviewer's case (several same-type events on one day) is real for ground units at lower echelons and for air and naval work, but **none of it is in the data today**: the rule cost nothing so far (0 exceptions) and has not yet caught anything either (the audit before the rule found 0 violations). (3) The rule's value will be greatest during 1945 batch work, when hundreds of rows are added at once; making it a warning then would lose the only check that stops accidental duplicates. (4) Relaxing it later is cheap and reversible: a validator severity change (error to warning), and the exception table stays as the list of acknowledged repeats. Propose: keep the error; revisit when the exception table has about ten entries, or before air or naval rows are added, whichever comes first; at that time consider an error for division echelon and above and a warning below. Docs only now: the heading and one sentence.
- **Owner's decision (26 October 2026):** the clarification was part of the approved documentation. **Done (commit 1):** `CONTRIBUTING.md` now headed "The duplicate guard": `claim_id` is the identity. The validator rule is unchanged.
