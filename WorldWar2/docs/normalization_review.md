## 3. Findings

Each finding: what it is, counts, risk if left, fix, effort, timing.

### F1. Command relationships live inside claims as JSON

- **What.** `command_relationships` is a JSON list in 551 claims (15 claims hold the string `unknown`). It is 219 KB, 27.2% of the claim-file bytes.
- **Counts.**
  - 1,061 entries collapse to 333 distinct (subject unit, higher unit, relationship) triples: 728 entries (69%) repeat an earlier triple, because every claim for a unit restates the relationship.
  - Every entry stores `name` (1,061 of 1,061). In 902 the name differs from `units.unit_name` (it adds a nationality prefix: "US VII Corps" vs "VII Corps"); 19 unit ids appear under 2 names ("US First Army" and "First Army"; "SHAEF" and the long name).
  - 16 entries have `unit_id` null with the free-text name "standing parent not identified" and relationship `unknown`; 15 claims have `parent_unit_id` = the string `unknown` (a sentinel in a foreign-key column).
  - Parent information is kept in four places: `units.parent_unit_id` (11 rows), `units.initial_parent_unit_id` (140 rows, with 81 month-only `as_of` dates), `claims.parent_unit_id` (566 rows; it equals one entry of the JSON in all 551 claims that have JSON, and differs from `units.parent_unit_id` in 562 of 566) and the JSON itself.
  - The derived `build/command_relations.csv` has 315 rows (US units, 24 July to 31 December 1944 only); it is rebuilt from the same JSON.
  - Temporal fields (`effective_from` 778, `date_basis` 784, `effective_to` 42, `ordered_date` 13, ranges 7) are embedded in the JSON and parsed by 3 scripts.
- **Risk.** Interval logic (who held whom at which hour) is relational work done on text; every new claim adds repeated JSON; a renamed unit means editing hundreds of strings; the table only exists for one army and one window.
- **Fix.**
  - Small, now: remove `name` from the entries (generate it from `units`); make `unit_id` required and add an explicit placeholder unit (or a `standing_parent_unknown` flag) instead of null; replace the `unknown` sentinel in `parent_unit_id` with blank plus a flag.
  - Large, before the next claim batch: `data/command_relations.csv` as the master (relation_id, subject_unit_id, higher_unit_id, relationship, valid_from, valid_from_latest, valid_to, valid_to_earliest, times, basis fields, note) with a join `command_relation_claims` (relation_id, claim_id) as evidence. `claims.parent_unit_id` becomes derived (or stays as a validated convenience column). The existing `build/command_relations.csv` logic, `who_controls.py` and the temporal audit already define the semantics; the migration is a restructuring of data they already read.
- **Effort.** Small step now; the table is large (about the size of the operations migration plus changes to 3 scripts).

### F2. No places table; place names carry qualifiers and provenance

- **What.** `location_name`, `latitude`, `longitude` and the coordinate source are stored per claim.
- **Counts.**
  - 421 distinct `location_name` values and 335 distinct coordinate pairs for 566 claims. 86 names are reused (231 claims); 94 coordinate pairs are reused (325 claims, 57%).
  - 42 coordinate pairs have more than one name (up to 8): the point 49.12, -1.09 is named "Saint-Lô", "Saint-Lô-Caumont gap sector", "Front before Saint-Lô (representative point)", "Southern front, First Army zone (representative point)" and 4 more, so the name carries claim context, not place identity.
  - 141 names carry a parenthetical qualifier (that is claim context, not place identity); 359 contain a comma (mostly an administrative tail such as ", Manche").
  - 3 names (the text before any parenthesis) are used with more than one coordinate pair.
  - Coordinate provenance is the tail of `source` (`; coords: ...`): 566 of 566 claims, 279 distinct strings, with variants of the same service ("Wikipedia" 192, "Wikipedia (en)" 140, "Wikipedia (fr)" 12, "OSM Nominatim" 14, "OpenStreetMap Nominatim" 4, and the rest with an embedded place name).
- **Risk.** No way to ask "all claims at Caen"; the same place can drift apart; nothing to join to GeoNames or Wikidata; Eastern Front place names (transliterations, renamed towns) will multiply the variants.
- **Fix.** `data/places.csv` (place_id, name, admin_area, country, latitude, longitude, coordinate_reference_id, wikidata_id, alt_names) and `claims.place_id` (nullable: a sector or front-line point that is not a named place keeps its own coordinates and `location_represents`). Qualifier text moves to a short `location_note`. The coordinate note becomes the place's `coordinate_reference_id` (R001 Wikipedia API, R002 Nominatim). Keep `latitude`/`longitude` on the claim for representative points and for consumers that want one flat file.
- **Effort.** Medium (a migration script plus 2 validator checks: the claim point equals the place point unless `location_represents` says representative; qualifier text not in the name).
- **When.** Before the next claim batch, while there are 421 names to reconcile by hand.

### F3. Unit references in text columns (`engaged_with`, `composing_units`, unit source columns)

- **`engaged_with`.** 157 claims, 200 entries, 60 distinct. 50 distinct entries resolve to a `unit_id` by name; 10 do not ("British Royal Air Force", "German Nineteenth Army", "Canadian 3rd Infantry Division" vs the unit name "3rd Canadian Infantry Division", "German 17th SS Panzergrenadier Division", and one entry broken by a comma inside parentheses). These are the source of 9 of the 12 current validator warnings. Two delimiter styles (38 cells with `;`, 119 single). Risk: opponents cannot be queried by unit; a spelling variant silently breaks a link. Fix: a join `claim_engagements` (claim_id, opponent_unit_id nullable, opponent_text, note) or at minimum an `engaged_unit_ids` column with the unresolved ones added as placeholder units. Effort medium.
- **`composing_units`.** 101 claims with a list, 8 `unknown`, 457 blank; 325 entries, 263 distinct, only 53 of them equal a `units.csv` name (the rest are regiments and battalions that are not units yet; some carry prefixes such as "attached: 2nd Canadian Armoured Brigade"). It is structured data (subordinate units on a date) stored as a string with a blank-means-unchanged rule that a join table cannot express. Fix: keep as text until regiment-level units exist; then `unit_composition` (parent_unit_id, child_unit_id, from, to). Effort later; now only forbid the `attached:` prefix.
- **`units.csv` sources.** `formed_date_source` holds a raw URL in all 234 non-blank cells (234 distinct) where claims now hold reference ids; `listing_source` and `initial_parent_source` hold 11 tokens (117 cells have more than one token, 15 are blank), mapped to references by `references_meta.source_token`; `build/unit_references.csv` is derived by matching. Risk: the same drift the claims had before `reference_ids`. Fix: `formed_date_reference_id` plus a `unit_references` master (unit_id, field, reference_id) or `reference_ids` on units, mirroring claims. Effort small to medium.

### F4. Unit table and identifier conventions

- **`parent_only` is redundant.** It equals `record_status == placeholder` on 354 of 354 rows; the vocabulary value `partial` is unused. Fix: drop `parent_only` (derive it). Small, now.
- **Names are not globally unique and are displayed with a prefix.** 11 `unit_name` values occur under 2 nationalities ("3rd Infantry Division", "XXX Corps", "VIII Corps", "Seventh Army"...); uniqueness holds only on (nationality, unit_name). The prefixed display form ("US VIII Corps") is stored in 1,061 command entries, in `engaged_with` and in validator logic (`ADJ` map). Fix: add `display_name` to `units` (generated from the nationality adjective) and use it everywhere text must be unique. Small.
- **`unit_id` encodes attributes.** Format `<nation code>-<arm or branch code>-<number><echelon letter>`; 10 nation prefixes (GER 209, US 84, UK 31, FR 13, CAN 9, ALL 3, POL 2, BEL 1, CZ 1, NL 1; each maps one-to-one to a nationality name); echelon letters D 208, C 67, B 20, A 19, H 6, G 3; 31 ids have no echelon letter (nickname and Kampfgruppe-style ids such as `GER-KG-BOEHM`, `NL-INF-IRNEB`); 2 ids ending `D` are regiment/battle groups, not divisions (the letter and the echelon column disagree). Because ids are never renamed, the embedded attributes can go stale (a redesignation, a brigade promoted to a division). Fix: document ids as opaque, keep the pattern validator, and move the nation code to a nationality table (F5). No renaming of existing ids. Small.
- **Units that are only skeleton.** 240 of 354 units (68%) are placeholders, 208 of them not referenced by any claim or by a parent column of another unit. This is the order-of-battle skeleton and `coverage.csv` already reports it. Keep, but see F5 for an `in_scope` flag if the skeleton grows beyond the claims.
- **Hierarchy semantics are ambiguous.** `units.parent_unit_id` (11 rows) is described as the standing parent; `initial_parent_*` (140 rows) as the parent at formation. With F1 done, both become rows in `command_relations` with a `relationship` of `organic`/`assigned`, and the two unit columns can be dropped.

### F5. Lookup tables and vocabularies

- **Present and fine.** Vocabularies for echelon, branch, theater, nationality, relationship, event type, confidence, precision, location basis, strength, operation types and reference roles are in `schema/vocabularies.json` and enforced. Counts used: 7 of 11 echelon values, 5 of 8 branch values, 2 of 8 theater values, 9 of 10 relationship values (`supporting` unused), 18 event types, 10 nationalities.
- **Missing or duplicated.**
  - Nationality has no code, adjective or side. The code is the unit-id prefix (10 codes), the adjective is a validator constant (`ADJ`) and the name prefix in JSON, and "Allied" (3 units: AFHQ, SHAEF, First Allied Airborne Army) is not a nation. Germany is `Germany` in units and claims, `German` in `operations.nationality_scope` (and in the vocabulary `operation_scope`), and `GER` in ids. Fix: `nationalities` (code, name, adjective, side, aliases) and `nationality_scope` using the same values. Small.
  - Echelon rank order is copied into 4 scripts (`validate.py` `ECH_RANK`, `audit_temporal_relationships.py` `RANK`, `who_controls.py` `RANK`, `build.py` `ECHELON_ORDER`), and the copies include `squad`, `platoon`, `company` and `battalion` that are not in the echelon vocabulary. `STANDING_RELS`, `HIGHER_THAN_ORGANIC` and `STANDING` are also constants in code. Fix: give each echelon a `rank` and each relationship a `standing` flag in `vocabularies.json`; read them from there. Small, now.
  - Vocabularies are duplicated between code and JSON: operation types, date bases, relations and scopes exist in `scripts/operations.py` and in `vocabularies.json` (equal today, no check); `REFERENCE_TYPES` is only in `validate.py`. Fix: single source in `vocabularies.json`.
  - `schema/*.json` declares primary keys but no foreign keys; all 9 foreign-key relationships (claim to unit, operation, reference, conflict group; unit to parent; operation to parent; relation endpoints; exceptions; roles) are enforced only by code. Fix: declare `foreignKeys` (Frictionless style) and generate checks from them where simple. Small.
  - `check_coordinates.py` has bounding boxes for 6 of the 8 theaters (none for `atlantic` or `other`), and the Pacific box stops at longitude 180.
- **Confidence, precision, location basis.** These are small coded vocabularies; keep as vocabularies, not tables (see section 4).

### F6. Derived values stored as data, and copies of tables

- `location_temporal_offset_days` is `location_date - date`: 354 rows, 0 mismatches, 0 rows with an offset but no `location_date`. Derive it in `build.py`; drop it from the claim files. Small.
- `strength_status` and `strength_json`: 13 rows have status `unknown` while a JSON exists, and 5 rows have a known status with no JSON; the two can disagree. Fix: derive the status from the JSON, or require the JSON when the status is not `unknown`. Small.
- `established`, `disestablished`, `destroyed` are 3 columns of 566 cells with 5 true values in total (established 1, disestablished 2, destroyed 2). `event_type` already has `activation`, `destruction`, `surrender`, and `units.formed_date` holds the formation date for 234 units. Fix: replace by a `lifecycle` value or rely on `event_type`; drop the 3 columns. Small to medium (they are in all_claims and the geojson).
- `references.csv` repeats 13 of the 16 columns of `references_meta.csv` and adds 5 counts, so a person editing a title opens the wrong file. Fix: one hand-edited table and a generated `reference_usage.csv` (reference_id, claims_count, units_count, operations_count, first_claim_id); or keep both and mark `references.csv` read-only with a banner row. Small.
- `claims.parent_unit_id` is derivable from the command relationships (551 of 551 contain it). Covered by F1.
- `all_claims.csv` repeats all claim columns plus 6 derived operation columns; `claims.geojson` repeats a subset. Both are generated and byte-checked in CI. Together 1.4 MB for 566 claims; `docs/roadmap.md` already plans to stop committing them. Keep for now (section 4).
- The `source` column duplicates `reference_ids`: 1,019 distinct `source` strings (1,246 URLs inside them) versus 1,528 reference links (the difference is the 561 coordinate-service links and similar); 164 claims share an identical `source` string with another claim. A consistency check exists. Fix later: generate the readable citation from `reference_ids` and `source_locator` and keep the free text only as `source_note`. Medium, later.

### F7. Reference tables

- **Roles table is mostly mechanical.** `claim_reference_roles.csv` has 619 rows, of which 561 (91%) only record that R001 (348) or R002 (213) is the coordinate service. Only 58 rows (3 location, 21 strength, 20 command_relationship, 12 date, 2 event) say something about evidence. This is my own design from the last change, and it is redundant: the `location` role of a `gazetteer_geocoder` reference follows from the reference's `source_type`. Fix: derive those rows and keep the file for human judgments only. Small.
- **Coordinate services count as references.** 306 claims have exactly two references, many of them one real source plus the geocoder (R001 and R002 are the only 2 `gazetteer_geocoder` references and make 561 of the 1,528 links). Counting geocoders as evidence overstates support: ignoring them, 391 claims (69%) rest on a single source family. Fix: move the coordinate service to the place record (F2) and keep `reference_ids` for evidence only; or exclude `gazetteer_geocoder` from the family rule. Small.
- **Work/part structure is flattened.** `source_type` counts: reference_compilation 194, encyclopedia 173, official_history 77, assignment_table 37, news_or_web_article 11, monument_or_memorial 6, archive_document 5, other 2, gazetteer_geocoder 2, unit_history 1. The 194 `reference_compilation`, 77 `official_history` and 37 `assignment_table` entries come from 2, 3 and 1 publishers and each carries its own `full_citation` (194, 77 and 37 distinct strings) and 2, 3 and 1 distinct reliability notes. Fix, optional: `works.csv` (work_id, citation, publisher, licence) and `reference_id -> work_id + part`. Low value at 508 references; do it if the references table is published as a bibliography. Medium, later.
- **Repeated descriptive text.** 33 distinct publishers, 19 licence strings, 30 reliability notes, 26 `used_for` strings over 508 rows. Keep as text (section 4).
- **Source family.** The vocabulary names 3 families (`wikipedia`, `us_army_cmh`, `openstreetmap`) but the references use 29 distinct `source_family` values (`wikipedia` 173, `lexikon_wehrmacht_de` 164, `us_army_cmh` 113, `ww2byday_com` 30, then 25 families with 1 or 2 references each, mostly host-name tokens). The independence rule is therefore not described by the vocabulary. Fix: a small `source_families` table (family, description, independent_of). Small.

### F8. Free text that holds structure (`notes`, `commander`, `location_name`)

- `notes` averages 337 characters and is 23.7% of the claim-file bytes. Labelled sentences: Event date 108, Event definition 106, Location 100, Relationship 100, Event support 70, Location support 70, Coordinates 55. 106 claims have 3 or more labelled sentences.
- Structured facts inside notes: 429 notes contain a "d Month" date; 42 mention another claim id; `source_locator` is filled for only 158 claims, so page or chapter locators that exist in notes (a few notes cite "Chapter" or "ch.": 3 and 6) are not in the structured field. The "Coordinates" sentence (55 notes) duplicates the coordinate note in `source`.
- `commander` is rank plus name plus asides in one string: 152 distinct strings, about 132 people. 17 people appear under more than one string (rank changes and punctuation variants); 19 cells embed an event (a relief, a death or a handover) in the string; 24 units have more than one commander string.
- **Fix.**
  - Small, now: normalise commander punctuation and move parentheticals into notes; add a validator check that a new note label is one of the 7 known labels.
  - Medium, later: `persons` (person_id, name, nationality, alt_spellings) and `unit_commanders` (unit_id, person_id, rank, from, to, basis, reference_id); the claim's `commander` becomes derived or a `commander_id`.
  - Medium to large, later: a `claim_evidence` table (claim_id, aspect = event | date | location | relationship | strength, statement, reference_id, locator). It is the natural successor to `claim_reference_roles` and to the Event support / Location support sentences (9.9 KB of text across 140 sentences), and it gives the roles table its judgment rows. Do not start before the label set is frozen.

### F9. Keys, natural keys and conflict groups

- `claim_id` is one global counter. Two contributors working in parallel will both take C0567. Fix: allocate ranges per batch or per contributor in CONTRIBUTING, or move to `<unit_id>-<date>-<n>` as a natural key and keep C#### as an alias. Small (a rule) or large (rekey, not recommended while claim ids are cited in 42 notes and in two exception tables).
- Natural key: (`unit_id`, `date`) is not unique (7 pairs, each two different events on one day); (`unit_id`, `date`, `event_type`) is unique (0 duplicates). Add that as a validator rule.
- Conflict groups: 14 groups (G001 to G014), 29 claims (5%), group size 2 (13 groups) or 3 (1), all within one unit. A claim that is not preferred must be in a group (0 exceptions). The group has no row of its own (no reason, no resolution note). Keep as is until there are more than about 50 groups; then a `conflict_groups` table (group_id, unit_id, reason, resolution).
- Date formats: claim, operation and command-entry dates are all `YYYY-MM-DD`. `units.formed_date` mixes full dates (199), months (19) and years (16); `initial_parent_as_of` has 59 full dates and 81 months. The validator accepts partial dates; that is fine, but sorting and "valid on date X" queries need a precision rule (a partial date means the whole period). Document it; no change.
- Same unit spelled several ways: 19 unit ids with 2 display names in command entries; "Canadian 3rd Infantry Division" vs "3rd Canadian Infantry Division"; `engaged_with` forms with and without the adjective (the validator accepts 3 variants per unit to cope). All of these disappear with ids (F1, F3) and a generated display name (F4).

### F10. Operations tables

- 36 operations, 12 operations + 12 battles + 9 campaigns + 2 phases + 1 umbrella; 5 are used by no claim (OP-CAMP-CENTRAL-EUROPE, OP-CAMP-SOUTHERN-FRANCE, OP-LUTTICH, OP-OVERLORD, OP-WACHT-AM-RHEIN). `operation_id` on all 566 claims resolves; `claim.theater` equals `operation.theater` in all cases (all 36 operations are `western_europe`).
- Open points: a single `theater` and a single parent per operation (`operation_relations` handles overlap with `related`/`concurrent_with` rather than membership); `nationality_scope` uses `Allied` 28, `All` 6, `German` 2 (F5); `reference_ids` is a `;` list in 36 of 36 rows with a derived join `build/operation_references.csv` (same pattern as claims, fine); `alt_names` is a `;` list in 14 rows.
- Fix when a second theater arrives: allow several theaters per operation (an `operation_theaters` join) and an optional second parent through `operation_relations`. Not now.
- `operation_exceptions` (11 rows) and `coordinate_exceptions` (5 rows) are tiny; give the reasons a short code and replace any raw URL by a reference id when touched. Small, optional.

## 4. Scalability: air, naval and Eastern Front data

- **`branch` and `echelon` conflate service, arm, organisation and size.** The `branch` vocabulary has 8 values (Army, Armoured, Airborne, Waffen-SS, Luftwaffe, Marines, Air Force, Navy) that mix a service, an arm (Armoured 63 units, Airborne 9) and an organisation (Waffen-SS 16). The 15 "Luftwaffe" units are all ground units (Fallschirmjäger divisions and corps, the First Parachute Army, and Luftwaffe field divisions and corps), so the one column already cannot say "air unit" versus "Luftwaffe-owned ground unit". `echelon` has 4 reserved values (`air_force`, `air_formation`, `fleet`, `naval_unit`) that fold wings, groups and squadrons into one value and ships into another, and the validator's `ECH_RANK` has no rank for them. Fix: split into `domain` (land / air / sea), `organisation` (Heer, Waffen-SS, Luftwaffe, US Army, USAAF, Royal Navy ...), `arm_or_type` (infantry, armoured, airborne, fighter, destroyer ...) and a per-domain `echelon` with a rank in `vocabularies.json`. Effort medium; do it before the first air or naval unit so no unit needs re-coding. Keep the current values as the land mapping.
- **Nationality and side.** `Allied` stands in for coalition headquarters (3 units). Add `side` (Allied / Axis / neutral) on the nationality table, and use `multinational` for coalition HQs. New values needed for Soviet, Italian, Japanese and others.
- **Theater.** One theater per unit (353 western_europe, 1 mediterranean), per claim (566 western_europe) and per operation (36 western_europe). Units change theater over time (a Mediterranean army that moves to France). Keep `theater` on the claim (it is the theater of that event), treat `units.theater` as a primary theater only, and let operations be multi-theater (F10).
- **Locations.** `location_represents` (6 values) assumes a land point. Ships and aircraft need `at_sea`, `airfield`, `area` or `track`; `precision_km` tops out at 50 (6 bands: 1, 3, 5, 10, 25, 50); the bounding-box check has no Atlantic box. A naval claim may need a polygon or a track, which a single point cannot hold; decide whether the dataset stays point-only (then fleets are a representative point with a large precision) before adding sea units.
- **Event types** (18) are ground-centred; add generic ones (`sortie`, `patrol`, `sinking`, `convoy`) when needed. Not an issue now.
- **Identifiers.** The `unit_id` pattern (`NATION-ARM-NNNE`) does not fit squadrons (RAF 617), ships (hull numbers) or Soviet fronts. Treat ids as opaque after F4 and let the validator check only the character set, uniqueness and prefix-to-nationality code.
- **Command relations.** `HIGHER_THAN_ORGANIC` and the echelon-rank checks are ground-only. Air units have operational and administrative chains at once (the relationship vocabulary already has `administrative_control`, 4 uses, and `supporting`, 0 uses); a relations table (F1) handles that, JSON in claims does not scale to it.
- **Files and build size.** Per-unit claim files (114 files, median 3 rows, 32 with a single row) suit human review today. At thousands of squadrons and ships the tree would hold tens of thousands of tiny files. Decide a threshold (for example 2,000 units): shard by nationality and domain, one file per formation family, and keep the per-unit layout for the ground order of battle. `build/all_claims.csv` and `claims.geojson` (1.4 MB for 566 claims, about 140 MB at 100 times the size) should stop being committed at the size `docs/roadmap.md` already names; publish them as release assets.
- **Eastern Front.** Sizes and ranks differ (front, army, corps, division); map `front` to `army_group` explicitly in the echelon vocabulary. Place names need alternate spellings and transliterations, which is another reason to do F2 first. Names of units need a display-name rule (F4).

## 5. What should NOT be normalized

- **`unit_name`, `nationality`, `echelon`, `branch`, `theater` repeated on each claim row.** They are 27,331 characters, 3.4% of the claim bytes, with 0 mismatches against `units.csv` in 566 rows and a validator error if one drifts. The repetition keeps each per-unit file and `all_claims.csv` self-contained for a person or tool that never loads `units.csv`. Keep it, add `theater` to the validator's equality check (it checks 4 of the 5 columns).
- **Latitude and longitude on the claim.** 219 of 566 points stand for an area or a line rather than a named place (`sector_center` 130, `front_line_point` 62, `main_body` 21, `approach_route` 6), and 279 are headquarters. Keep the coordinates on the claim even after F2 adds `place_id`.
- **`reference_ids` as a list in the claim file with a derived join.** One cell, one file to edit; the join table is generated and checked. A master join table would put one citation in two files.
- **`confidence`, `precision_km`, `location_basis`, `location_represents`, `claim_status`, `strength_status`.** Small coded vocabularies with 4 to 8 values each; a lookup table adds a join and no information. Keep them as vocabularies in `vocabularies.json`.
- **`strength_json`.** 20 rows. Keep the JSON until it passes about 100 rows, then a `strengths` table (unit_id, as_of, personnel, tanks, ... basis, reference_id).
- **Partial dates in `units.csv`.** The `YYYY`, `YYYY-MM`, `YYYY-MM-DD` forms are valid ISO 8601 prefixes and reflect what sources give. Document the rule instead of splitting date and precision columns.
- **Descriptive text in the references (publisher, licence, reliability, used_for).** Free text repeated over 508 rows is cheaper to edit than 4 lookup tables.
- **Per-unit claim files and committed `build/` outputs, for now.** They make diffs and pull requests readable and let GitHub render the data; revisit at the thresholds in section 4.
- **Conflict groups as a bare id.** 14 groups, no attributes; promote to a table only when groups need a reason or resolution.
- **The `data/operation_exceptions.csv` and `coordinate_exceptions.csv` side files.** They are exception lists by design (16 rows together).
- **The claim as the wide event row.** Splitting a claim into place, commander, relation, strength and evidence tables everywhere at once would give a dozen joins for 566 rows. Normalize the parts that repeat (relations, places, opponents, commanders) and leave the event row flat.

## 6. Suggested order

1. **Now (one small schema change, no new tables of substance):** drop `parent_only`; remove `name` from command entries and forbid null ids; replace the `unknown` parent sentinel; derive `location_temporal_offset_days`, `strength_status` and the 3 lifecycle booleans; stop storing the 561 mechanical role rows; add nationality and echelon-rank data to `vocabularies.json`, one name for Germany, declare foreign keys; add the (unit, date, event_type) uniqueness rule; normalise commander strings.
2. **Before the next claim batch:** `places` (F2), `command_relations` as master (F1), `engaged_with` and unit source columns as ids (F3).
3. **Before the first air, naval or Soviet unit:** the domain / organisation / type / echelon split and the nationality-side table (F5, section 4); decide point-only versus track locations; add a file-sharding rule.
4. **Later:** commanders (F8), `claim_evidence` (F8), works table (F7), `unit_composition` (F3), multi-theater operations (F10), generate `source` from `reference_ids` (F6).

Each step follows the pattern used for `operation_id` and `reference_ids`: a migration script in `scripts/` that is deterministic and idempotent, a validator rule that makes the old form an error, derived outputs rebuilt by `build.py`, and a methodology paragraph that says what was chosen and why.
