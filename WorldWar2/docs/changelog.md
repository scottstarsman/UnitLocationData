## batch5-apr-may-1945: relations closed by the CMH table end (27 October 2026)

Seventh commit of Batch 5, found by a check after the three claim commits. **`data/command_relations.csv`: 9 existing open relations closed with the end the CMH ETO-OB table gives; `data/command_relation_claims.csv`: 10 links changed to carry the end; the claim notes that print the relation dates and the build files were regenerated. No claim, place or unit was added or removed.** The relation planner closed an open relation only when a new claim listed a replacement of the same kind; these 9 had no replacement in the dataset (the unit moved to a higher unit that has no record, or the table simply stops listing it), so they would have stayed open past the table end (for example the 100th Division's VI Corps relation after the table's row of 25 April 1945, which lists no corps). Rule applied: the end is the day before the first table row that no longer lists the entry (the table-end rule used for `CR0447`); where a Batch 5 claim of the unit lists the relation on a date up to the end, that claim's link carries `asserts_end` (or `asserts_start_and_end`) with `stated_effective_to` and basis `assignment_table` (the same pattern as `CR0447` in the corps follow-up), `end_unknown` false; where none does, the end is recorded as `inferred_from_next_claim` with `valid_to_earliest` the last claim that listed it. Each relation carries the old, new and reason in its own note. Where a table lists an entry in more than one run (for example the 2nd Division's V Corps), the relation is closed at the last end and the note says the gaps are not modeled, as for the other table relations. ## integrity-rules (26 October 2026)

Three data integrity rules, one commit each: the claim key (this section's first item), claim-id allocation, and the controlled set of note labels. Validator warnings stay the same three; no claim was changed.

### Rule 1: unit, date and event type identify one claim

- **Rule.** `(unit_id, date, event_type)` is unique across the claims (`uniqueTogether` in `schema/claims.schema.json`, enforced by `scripts/validate.py`). A repeat is allowed only inside one conflict group, or when the pair is listed with a reason in the new hand-maintained table `data/claim_key_exceptions.csv` (`claim_id, other_claim_id, reason`: several actions of one kind by one unit on one day). An exception that is not needed is an error, so the list cannot go stale. The error names both claims and the three ways out. Described in `schema/README.md` ("Claim key") and `CONTRIBUTING.md` ("Claim identity", checklist).
- **Audit before the rule.** 566 claims, 566 distinct keys: **0 violations**, so no claim was deleted, merged or edited and the exception table is empty. Looked at for context: 7 pairs of claims share a unit and a date but differ in event type (C0015/C0016, C0199/C0200, C0284/C0483, C0484/C0485, C0333/C0496, C0217/C0481, C0220/C0482: a landing or attack beside a headquarters move, and so on); they are different events and stay as they are. The 14 conflict groups all differ in date or event type (sources disagree about the date), so none needed the group exemption either.
- **Table.** `claim_key_exceptions` is declared in `schema/relations.schema.json` (primary key `claim_id, other_claim_id`, both foreign keys to `claims.claim_id`).

### Rule 2: claim ids

- **State first.** 566 claims, C0001 to C0566, every id once, no gap; every claim id that appears in any of the 38 revisions of the working history is still a claim (no retired id exists). So the new table starts empty.
- **Rule** (`CONTRIBUTING.md`, "Claim ids"): format `C` + at least four digits; next id = highest id in use (claims and retired) + 1; an id that was on `main` stays with its claim, is never reused and never renumbered (a branch renumbers only its own unmerged new ids if two branches took the same number); gaps are allowed (an id that was never used); a claim that has to leave the data is retired in the new hand-maintained table `data/retired_claims.csv` (`claim_id, replaced_by_claim_id, reason`) in the same change; a merely wrong claim is corrected or contradicted, not retired.
- **Validator.** Ids are unique (as before); `data/retired_claims.csv` is checked (header, sorted, no repeated id, a retired id is not a claim, the replacement is a claim, the reason is not blank); a gap that is not retired is printed as a NOTE (none today). Declared in `schema/relations.schema.json` (`retired_claims`, foreign key `replaced_by_claim_id`).
- **History check.** `scripts/check_claim_ids.py [--base REV]` (default `origin/main`) compares with an earlier revision and fails when a claim id of that revision is gone without a retired row, now belongs to another unit, or when a retired id was forgotten or reused. A single checkout cannot show this and CI checks out one commit, so it is run by hand before a pull request (listed in the checklist).

### Rule 3: the note labels are a controlled set

- **Set found.** Sentence-initial `Label: ` phrases of label shape (a capital letter, then at most two lower-case words) in the `notes` of the 566 claims: 19 labels, 632 uses in 118 claims: Event date 108, Event definition 106, Relationship 102 (two with the qualifier `(sequence)`), Location 100, Event support 70, Location support 70, Coordinates 55, Objective check 8 (five with `(Batch 2 review)`), Location caveat 3, and one each of Location approximate, Location support fallback, Coordinate check, Command support, Opponents, Commander, Context, Later, Search, Review. Lead-ins that name a source, a batch or an id (`CMH ETO-OB chronology:` 17, `Wikipedia:` 15, `Batch 2 review:` 10, `Breakout-NN pNNN:` and others) are prose, not labels, and stay unchecked; no note was changed.
- **Vocabulary and check.** New vocabulary `note_label` in `schema/vocabularies.json` (value = definition and the frozen count). `scripts/validate.py` (`check_note_labels`) rejects a sentence-initial phrase of label shape that is not in the vocabulary (`unknown label`), and a known label with the wrong case or spelling; a qualifier in parentheses is free. `Wikipedia` (a source name of label shape) is exempted by name.
